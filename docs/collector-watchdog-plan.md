# DC / TG / QQ 独立巡检交接方案

本文件仅定义后续实施方案，未安装巡检脚本或 Windows 任务。当前三个业务进程仍独立运行。

## 已确认的问题与现有接口

2026-11-26 04:09 左右（北京时间），TG 网络连接关闭后，Telethon 向 stderr 输出 WARNING。Windows PowerShell 5.1 在 `$ErrorActionPreference='Stop'` 且重定向输出时将其转为 `NativeCommandError`；启动外层捕获到 `RemoteException` 后退出。已用模拟原生进程复现。启动脚本需要保留警告，并依据 Python 退出码判断失败，避免抢先终止 Python 的重连循环。

现有数据根目录由 `MUSE_DATA_DIR` 指定，默认是项目的 `data`。巡检必须与被检查进程使用同一个项目、数据目录和 Windows 用户，以便使用既有加密凭据；主机连接参数仅从本机连接配置读取。

| 进程 | 已有检查入口 | 已有信号 | 还需补充的业务信号 |
| --- | --- | --- | --- |
| DC 采集 | 本机 `127.0.0.1:8765/v1/health` | `role`、`started_at`、`last_capture_at`、`received`、`at` | 各启用频道最近浏览器扫描/页面上报、采集错误、入库错误 |
| TG 采集 | `data/telegram/monitor-status.json` | `at`、每来源 `status/error`、`scan_until`、完整扫描标志、读取/写入/验证数量 | 更完整的脱敏错误类别、每轮开始和结束时间、正在执行的阶段 |
| QQ 发送 | 本机 `127.0.0.1:8766/v1/health` | `online`、`planners`、`outbox`、`telegram_collector`、`at` | 最近 Gateway 心跳确认、规划开始/结束、最老待发年龄、发送成功时间和最近错误 |

HTTP 检查在内存中读取 `data/collector-token.txt`，通过既有 `x-collector-token` 鉴权。不得将令牌、会话、正文或密钥写入巡检结果。`running` 表示 QQ 当前是否正在处理一轮任务，不能当作是否常驻的判断。健康接口的 `at` 仅证明 HTTP 能响应，不能证明规划和发送进度正常。QQ 返回的 `telegram_collector` 是 TG 状态文件的副本，仍需独立检查进程和时间。

## 巡检与故障分类

建议 Windows 任务计划每分钟执行一次短巡检，配置不允许重叠执行。检查请求设超时；记录最近成功时间、首次异常时间、连续失败次数和状态变化。需要更快展示时可缩短周期，或为状态查看增加只读界面。

| 异常 | 判断依据 | 建议处理 |
| --- | --- | --- |
| 进程退出 | 精确匹配本项目入口与数据目录，没有对应进程 | 确认服务已启用且未人工暂停后，仅拉起该进程 |
| 进程存在但接口超时 | 连续多轮请求失败 | 先告警并保存有界诊断；确认卡死后再按策略恢复 |
| TG 扫描停滞 | 进程存在，扫描进度长期不推进 | 结合当前阶段、下载和限流状态判断；建议超过 180 秒先告警，避免正在补采时重启 |
| 源没有新消息 | 扫描持续成功，但写入数量为零 | 正常；不能用最后消息时间单独判断故障 |
| 网络/平台暂时断开 | Gateway 短暂离线、TG 连接错误、HTTP 5xx | 优先让已有退避/重连逻辑恢复，持续异常再告警 |
| 授权或权限失败 | TG 会话失效、无频道权限、QQ 鉴权失败 | 记录来源和类别，等待人工处理；禁止重启风暴 |
| SQLite 或数据错误 | 锁、磁盘写入失败、约束错误、时间戳缺失 | 区分短暂繁忙与持续数据错误，保留检查点和坏记录身份；禁止删除数据库 |
| 附件失败 | 图片下载、文件缺失、HTTP 404、哈希验证失败 | 按来源记录并保留重试/阻塞状态；进程重启无法修复源端失效图片 |
| QQ 积压或规划失败 | 规划器报错、待发数持续增长、最老待发年龄增长 | 按来源和目标群分别观察，结合已有每群两秒间隔及限流等待时间判断 |
| QQ 发送结果未知 | `unknown` 发送记录 | 保留隔离及人工核对流程，禁止自动重发 |

Windows Python 虚拟环境可能出现启动器与实际 Python 子进程的父子链；不能因为命令行相同就将其中一个视为重复实例并杀掉。应结合入口、数据目录、父子关系和已有业务锁确认实例。Node 入口也需精确匹配，避免误管其他项目。

## 有限恢复与审计

- 每角色独立启用/暂停与恢复开关，人工停用时不自动拉起；所有恢复动作尊重该开关。
- 对进程缺失先做连续确认，启动后给恢复宽限期；已有 QQ PID 锁、TG 文件锁继续生效，避免双实例。
- 可从每角色十分钟最多三次恢复、失败逐次退避起步；达到上限只告警，保留原因。
- 每次启动记录角色、原因、时间、PID、结果与退出码；日志按日期轮转。遇到网络警告要保留输出，依据实际退出码判断失败。
- 统一状态建议写入 `data/health/collector-status.json`，原子替换；另写脱敏状态变化事件。数据库默认只读检查，不改来源启用时间、检查点、待发任务或历史记录。
- 确保巡检任务自身失败后有重试策略和运行记录；不能依赖聊天窗口或 SSH 会话存活。任务按既有凭据所属 Windows 用户运行，并核对登录方式与重启后行为。
- 告警通道应独立于被监控的 QQ Bot；具体通道由后续实施者与用户确定，本文不授权发送测试通知。

## 验收

使用隔离数据与模拟传输验证：单进程退出只恢复该角色、连续故障触发恢复上限、人工暂停被尊重、巡检任务不重叠、没有新消息不告警、网络警告不导致 TG 退出、TG 长时间补采不被误杀、规划器失败能被发现、鉴权失效不反复重启、`unknown` 不重发。随后在远端验证三角色状态持续推进及重启后的任务运行情况。
